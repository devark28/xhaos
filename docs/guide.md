# User guide

How Xhaos works once it is running: workspaces, models, projects and agents, the sandbox and approvals, channels, secrets, and the rest of the page. To install it, see the [README](../README.md); to run it on a server, [deploy.md](deploy.md).

## Workspaces and sign-in

A workspace is a separate set of agents, projects, channels, memories, model providers, MCP servers, secrets, skills and search settings, with its own passphrase. The page opens on a picker, one card per workspace (like profiles): choose one and enter its passphrase. The first visit names the first workspace and sets its passphrase (at least 12 characters). **New workspace** asks for the new workspace's name and passphrase, and the passphrase of any existing workspace, so someone who merely reaches the page cannot create one. Inside, the workspace's name sits in the middle of the header; the `xh` logo leaves it: this browser is signed out of it and the picker shows again (its agents keep working). Each sign-in form uses the workspace's name as its username, so a password manager keeps one entry per workspace.

A workspace's passphrase does two jobs:

- **Sign-in.** A sign-in sets an HttpOnly, SameSite=Strict session cookie (30 days, kept in server memory) for that workspace. Every runtime call and the live event stream need one, and a session reaches only its own workspace: the server checks every call before running it (every service method names its workspace, which a test enforces for each bound method) and sends each page only its workspace's events. Only the page's static files, `/health`, and the sign-in endpoints answer without a session. Wrong passphrases slow down further attempts. Wails already refuses foreign `Origin` and rebound `Host` headers; the sign-in endpoints do the same.
- **Key encryption.** Argon2id turns the passphrase into a key-encryption key that wraps the workspace's own random data key, and that key encrypts the workspace's provider keys, MCP secrets, secrets and search key (AES-256-GCM). Only wrapped keys are stored (the `vaults` table). After a restart every workspace is locked: its agents and MCP servers wait until someone signs in to it, which unwraps its key into memory; another workspace stays locked. Changing a passphrase (Settings → Passphrase) rewraps the same key, so nothing is re-encrypted. **Lock workspace** there forgets the key and signs every browser out of it (its agents pause until someone signs in again); **Sign out**, like the logo, only signs this browser out. There is no recovery: a lost passphrase means entering that workspace's keys again. A server from before workspaces keeps everything: its single passphrase and key become the first workspace's.

Workspaces separate your work within one Xhaos. Agents of every workspace still run as the same system user (each command confined to its project by the sandbox), so for people or clients who must be protected even from a flaw in Xhaos, run separate instances (see [deploy.md](deploy.md)).

## Models

Models come from providers you add in the Models section of Settings (or `/providers`). Two kinds are supported: Anthropic (an API key) and OpenAI-compatible, one adapter for any endpoint that speaks Chat Completions with streaming: OpenAI, DeepSeek, and local servers such as Ollama, llama.cpp, or vLLM. Presets fill in each one's base URL; add as many OpenAI-compatible providers as you like, each with its own ID. Their key is optional (local servers take none), and leaving the model list empty asks the endpoint which models it offers. Test lists the models to check the key or endpoint. A third kind, Simulated (the "Simulated (no model, no tokens)" preset), calls no provider at all: a scripted stand-in drives the real harness so you can try approvals, channels and subagents for free. Its agents list the project and read a file, then act on words in the task: "split" or "spawn" starts two subagents and summarizes their answers, "contact #N" opens a channel with agent #N, "ask" asks you a question, "write" writes `sim-notes.md`, and "run" runs `git status`. A message from another agent gets one reply. `scripted` types at reading speed; `scripted-fast` doesn't wait. Keys are encrypted at rest under the passphrase (see above) and never sent back to the page. The server makes the model calls, so a local endpoint's URL is as seen from the server.

## Projects, agents and tools

Agents work in projects: folders on the server that you register in the Files tab of the side panel (`-root DIR` registers a folder at startup; without it nothing is registered, and agents can be created once a project exists). Each agent belongs to one project and its tools only reach that folder; agents in different projects coordinate through channels. The Files tab lists the projects, expands each into its folder tree, adds projects by server path, and removes ones no agent uses (the folder itself is untouched). Double-click or Ctrl+click a project (or Alt+Enter) to attach it to the composer, like an agent: new agents then start in it; without one they start in the first project, and subagents always use their parent's. A message never moves an agent to another project: sending with a project attached to agents that work elsewhere is refused with a note naming the agent. Agents have these built-in tools: `list_dir`, `read_file`, `search`, `write_file`, `edit_file`, `bash`, `ask_user` (questions for you; see below), `read_attachment` (see Attachments), `secrets_list` (see Secrets), `skill_read` (see Skills), and `web_fetch` and `web_search` (see Web). File paths are confined to the agent's project, symlinks included, and the file tools cannot write inside `.git` (a hook there would run on commit). `bash` runs in the project but can reach anything the server user can, so each command line is classified first: read-only commands (`ls`, `cat`, `grep`, `rg`, `find` without `-exec`/`-delete`, `git status`/`log`/`diff`/`show`/`branch` listings, and pipes of these) run at once; local git changes (`git add`, `git commit`, `git switch`, `git switch -c`) run without asking under auto review; anything else, including `git push`, always asks. A line is only read or git when every command in it is on those lists and it has no redirection (except to `/dev/null` and between its own output streams, like `2>/dev/null` or `2>&1`), command substitution, background job, environment prefix, absolute or `..` path, or `git -C`/`-c`/`--output`.

### Commands and the sandbox

Commands also run in a sandbox (`-sandbox auto`, the default; `on` refuses to run commands without one; `off` disables it). The server starts itself again as a small helper that locks itself down with Landlock, the Linux kernel's access control for unprivileged processes (Linux 5.13+; no root, no user namespaces, works in containers), then runs `bash`. Inside, a command can read and write its project folder, a temp folder of its own under `/tmp/xhaos-<uid>/sandboxes/` (its `TMPDIR`, cleared by the system), and a shared cache beside the database (its `HOME` and the Go and npm caches live there), read and run system files and the toolchains on `PATH`, and read the git identity (`~/.gitconfig`). When the project is a git submodule or worktree, its `.git` is a file pointing into the parent repository (`gitdir: ../.git/modules/name`); the sandbox follows it and lets commands use that git folder (and a worktree's main repository), and nothing else of the parent. It cannot read the rest of the home folder (other projects, `~/.ssh`, Xhaos's database, transcripts, attachments and key file), cannot read other processes' environments, cannot signal processes outside the sandbox, and cannot open Unix sockets (a seccomp filter: Landlock before ABI 9 does not cover connecting to socket files, so otherwise a command could use your SSH agent, the keyring, D-Bus or the Docker socket by path; pipes and `socketpair` still work). Network access is not restricted for ordinary commands; commands given secrets can reach only those secrets' hosts (see Secrets). Settings → Tools shows whether commands are sandboxed. MCP servers are started by the server itself and are not sandboxed.

### What auto review runs without asking

For read-write agents on auto review, the project's own build, test and lint commands run without asking. A built-in list decides this with no model and nothing to install, and it is on by default; the switch in Settings → Tools → Commands turns it off, together with the model. The list covers `go build`, `go test`, `go vet` and `gofmt --check`, `npm test` and `npm run` of the `build`, `lint`, `typecheck` or `test` script, `make` with no target or with `build`, `test` or `lint`, `pytest`, `tsc --noEmit`, `eslint`, `prettier --check`, `vitest run`, `cargo build`, `test` and `clippy`, `ruff check`, and a few more.

`npx`, `pnpx` and `bunx` are on the list only for a JavaScript tool that is already installed in the project's `node_modules/.bin` (`npx tsc --noEmit`, `npx vitest run`), with the flags the tool's own command takes. Anything else with them asks, since they would download a package.

These commands run inside the sandbox as usual, and with four caveats:

- `make` with no target runs the Makefile's default target, whatever that is.
- `go test` and `cargo` may download dependencies from the network when they are missing.
- `npm test` runs whatever script `package.json` names.
- Sandboxed commands have network access: ordinary commands are not network-restricted yet (only commands given secrets are limited to those secrets' hosts).

Commands with secrets, network tools, installs, publishes, deletes and anything outside the project still ask.

### The optional classifier model

A server can also run the optional classifier model (the installer's `classifier` part, off by default: see the deployment guide). It is a long-tail step for read-write agents on auto review: a small model on the server judges the commands the list does not match and the gate would otherwise ask about. It follows the same limits: the commands above still ask whatever the model says, and so does every command when the model is slow, down or unsure. It can only make a command run, never block one; the card of a command it allowed gives its reason. Turn the model on or off for the whole server in Settings → Tools → Commands. Developer → Keep classifier decisions (off by default) logs each of its decisions beside the database.

### MCP servers

MCP servers add more tools. In the Tools and MCP section of Settings (or `/tools`), add a local command (stdio; the Xhaos server starts it as its own user) or a remote URL (Streamable HTTP); env vars and headers are encrypted at rest and never sent back. The server keeps a session per enabled server, lists its tools there, and offers them to agents as `mcp__<server>__<tool>`. Their calls pass the same gate: each server's trust decides how. "Ask every call" (the default) always waits for you, "Run under auto review" behaves like a file write, and "Read-only" runs at once. A server's own read-only hints are shown but never trusted.

### Approvals

Every call passes the policy gate first. Reads run at once. With the default policy, writes and commands wait: the card shows each call with its diff or command and Allow/Deny, and `Allow all N` when several wait. A read-only agent has writes and commands denied; `git commit`/`git push` follow the commit setting even under auto review, and a push always asks. Once every waiting call is decided, the allowed ones run in order and the model gets all results (denials as errors). Owner messages sent while calls wait reach the model after the results. Stop (agent menu, or `/pause`) cancels the running turn and kills a running command with its children; the agent pauses and your next message continues it. Terminate ends the agent and its subagents and denies their waiting calls. Agents left running by a stopped server continue on the next start.

### Side questions: `/btw`

`/btw <question>` asks the composer's model about your agents ("what is #12 doing?", "summarize everyone's status") from a read-only digest of each agent's project, status, waiting calls, and recent transcript (channel messages marked with their sender, attachments by name, compaction summaries left out), plus the workspace's channels with their latest messages and its memories; the answer shows above the composer and nothing is written to any agent. Agents have no such tool; they will coordinate through channels. The log shows warnings only unless you pass `-verbose`.

## Data and backups

State lives in SQLite at `~/.local/share/xhaos/xhaos.db`, outside the repo. Each agent's transcript (messages, tool calls and their output, status changes) is written as JSON Lines to `transcripts/<workspace>/<agent>.jsonl` beside the database: one self-describing line per event (`seq`, `at`, `agent`, `kind`, `data`), readable with `tail -f`, `grep` or `jq`. SQLite stays the index: each event's row keeps its sequence number, kind, and where its line is, so ordering, catch-up and transactions work as before, while large bodies stay out of the database and its write-ahead log. A line whose transaction rolled back can remain in a file, but no row points at it. Workspace-level events (memories, closed channels) and rows written by older versions keep their body in SQLite. Back up the `transcripts` folder with the database.

## Attachments and Markdown

Both the top composer and the inline new-agent form accept multiple files through the **＋** attachment control, drag/drop, or pasted images. Documents and other file types are preserved as files. Pasted text of 4,000+ characters or 40+ lines becomes a `.txt` attachment automatically. Remove pending files with their × button.

Both inputs share a native `<xhaos-input>` rich-text component. Ctrl/Cmd+B and Ctrl/Cmd+I apply visible bold and italic through browser editing, without showing Markdown markers. There is no formatting toolbar. Rich content serializes to Markdown for task storage and model delivery. Plain Markdown can still be entered or pasted; sent messages render headings, emphasis, lists, quotes, links, inline code, and fenced code. Pasted HTML is not inserted into the editor.

Attachments can be sent with a new task, `/new task`, `tell agent 11 message`, or `/tell 11 message`. Attachment-only submissions create a task to review the files. With a backend, files are uploaded to the server (up to 20 MB each): the bytes are stored as files in `attachments/` beside the database, and SQLite and the event log keep only their name, type, and size. The model receives images (PNG, JPEG, GIF, WebP) as images and PDFs as documents (OpenAI-compatible providers get a note instead, as Chat Completions has no portable PDF input). Text files up to 100,000 characters are inlined after the message; a longer one sends its first 20,000 characters and a note with its id and length, and the agent reads the rest with `read_attachment` (id, character offset, limit up to 100,000), in as many parts as it needs. It can only read files that were sent to it. Other binaries become a note with their name and size. Attachments are read when each turn is built, so they also count toward the context budget until compaction summarizes them. In the prototype (no backend), files persist as blobs in IndexedDB. Either way, expand the task to download attachments or view raster images inline. Files are never executed. Storage failures keep the pending attachments for retry. Files waiting to be sent are lost on reload (the unsent text is kept; see Cards, titles, usage and appearance). Clearing browser site data removes stored attachments.

## Using the page

- The agent view opens in a single workspace context. Workspace connection/creation is reserved for a separate entry flow; there is no workspace management rail.
- Two-column mode uses independent sticky stacks: a short column stays visible while a longer column scrolls. Columns taller than the viewport stop when their bottom reaches the viewport bottom. Expanding cards and resizing the window recalculate that limit. Single-column and mobile layouts scroll normally.
- Agent transcripts start collapsed. Subagents stay inside expanded parent cards with indentation and connectors. Parent headers show subagent ID chips; click a chip to open that subagent inside its parent. Use chevrons to expand transcripts, and `/layout 1`, `/layout 2`, or `/layout 3` to choose column count.
- Tool calls and code have no nested boxes; lightweight lexical coloring distinguishes JavaScript, Rust, JSON, shell commands, and diffs. Tool output still expands inline.
- Status uses vivid dots: green for running, blue for complete, yellow for attention. Paused agents show no status dot. Attention uses an expanding ring around a solid dot. New attention requests scroll into view once, without changing keyboard focus or opening collapsed trees. A parent shows only its own status dot; a waiting subagent is indicated only by its own dot (on its header and its ID chip), never by an extra dot on the parent. Reduced-motion preferences disable animation and smooth scrolling.
- Allow/Deny acts on the request shown on that card. Pause/resume buttons are removed; the legacy slash commands still change mock state. Open the ⋯ menu after the chevron and choose Terminate agent to terminate an agent and its subagents; `/history` retains its transcript and can bring the terminated card back into view without restarting it. Menus also attach/detach recipients. Termination marks the whole subtree as terminated and preserves tasks, attachments, and history. This is local state only until the backend can cancel running work.
- Expand an agent or subagent to read multi-step sample conversations and saved notes inline. Click a tool call or edit to reveal its output or diff. Samples include shell commands, MCP calls, and approval requests; none are executed. Existing seeded tasks receive these sample transcripts without clearing saved state.
- The composer is the only way to create agents; there is no New agent button or draft card. With no recipients attached, Enter creates a new agent from the text, and the placeholder says "New agent". With recipients attached, Enter messages them, and the placeholder names them. `/new task` with one agent attached creates a subagent of it. `Ctrl/Cmd+Alt+N` detaches all recipients and focuses the composer. The model for new agents is a borderless dropdown next to the composer's attach button; it is hidden while recipients are attached and is remembered per browser. Anthropic entries are real API model IDs (`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`); the others are prototype labels until the backend lists configured providers. The selection is saved with the agent; on the backend page the list comes from configured providers and the agent runs on that model.
- Click an agent header or its chevron to expand/collapse the transcript. Double-click (or Ctrl/Cmd+click, which never waits) the agent header to attach or detach it as a composer recipient; with the header focused, `Alt+Enter` does the same. The `#ID` is a label, not a separate button. You can select several agents, then send normally; detach with × on a recipient chip or repeat the attach action.
- `Ctrl/Cmd+K` focuses the composer.
- Type `/` to open the command menu. Commands include `/new task`, `/search query` (or `/search` to clear), `/mcp`, `/memory`, `/layout 1|2|3`, `/channels`, `/history`, `/terminate`, `/allow`, `/deny`, and `/help`. `/allow`, `/deny`, `/pause`, and `/resume` act on eligible attached agents, or accept one explicit agent ID. Ineligible targets are skipped and reported. Questionnaires require answers, not approval; `/allow` and `/deny` never answer or dismiss them. `/help status` shows the real status dots and attention pulse; it is also linked from help. Older `/approve` and `/decline` aliases remain supported. Arrow keys navigate the menu; Escape dismisses it. Enter submits the composer; Shift+Enter adds a line.
- The page has two columns. On the left, the composer sits above the scrolling agent area, with Expand/Collapse all and the 1/2/3-column layout buttons in a bar above the agents; search is available through `/search`. The logo sits at the top left, beside the Message/Draw tabs. On the right, the side panel is always open at 30% of the width; its tab icons (Questions, Files, Channels, Memories, Nodes, Settings; Settings has Models and Tools and MCP as sections that expand in place) stay at its top and switch what it shows. On narrow screens it sits below the agents. Panels never replace the composer, so you can keep typing while one is open. Neutral surfaces use grayscale; only agent status dots use semantic colors.
- Dictation records one take from the microphone and sends it to the server, which transcribes it with a local speech sidecar. Click the mic to start and again to stop (five minutes at most; from 4:30 the timer shows the time left). While the take is transcribed the mic spins, with the time so far against an estimate (15 s per minute of speech until a take has been timed, then the last timed speed). The transcript lands in the composer for review; nothing is sent. The mic is hidden when the server has no sidecar.
- Dictation language (Settings → Dictation) is server-wide and English by default. Auto-detect works from the start of each take and can guess wrong on a quiet start. The server passes the language to the sidecar as `{language}`.
- Dictation hints (Settings → Dictation) are the words and names this workspace uses, as a text box of up to 1000 characters. The model reads only about the first 150 words (it keeps 223 tokens of hints, and names cost several each), and the box warns past that. Best as one punctuated sentence or a list of the words actually said. The server passes them to the sidecar as `{prompt}`, and the reference sidecar uses them as faster-whisper hotwords, which apply to every 30-second window of the take.
- Keep dictation recordings (Settings → Developer, off by default) saves each take as a WAV in `dictation-debug/` beside the database, with a line per take in `log.txt`: the time, length, loudness, transcription time, outcome and the start of the transcript. These are voice recordings; Delete all recordings removes them.

### Setting up the sidecar

Xhaos runs the program named by `-dictation-cmd` once per take, with the take as a 16 kHz mono 16-bit WAV, and reads the transcript from its stdout. The flags are:

- `-dictation-cmd`: the program. Empty turns dictation off.
- `-dictation-args`: the argument template, split on spaces. `{wav}` is the WAV path, `{model}` the model directory, `{language}` the dictation language (`en` by default, or `auto`), and `{prompt}` the workspace's hints. A field with `{prompt}` inside it (such as `--prompt={prompt}`) gets the hints as one argument, spaces and all.
- `-dictation-model`: the model directory, for `{model}`.
- `-dictation-timeout`: a fixed time limit per take. By default it is 60 seconds plus one and a half times the take's length (8.5 minutes for five minutes), so a slower server has room to load the model and transcribe. On timeout the sidecar's process group is killed. This is a limit, not an estimate: the estimate shown while transcribing comes from this server's last 8 takes (a fixed start-up part plus a per-second rate, kept in the database so it survives a reload and a restart); before the first take it assumes a laptop's speed.

`scripts/dictation/stt.py` is the reference sidecar, using faster-whisper with the CTranslate2 build of a Whisper model. Install it with `pip install faster-whisper`, then start Xhaos with the model directory:

```sh
xhaos -dictation-cmd /usr/bin/python3 \
      -dictation-args "/opt/xhaos/scripts/dictation/stt.py {wav} --model {model} --language={language} --prompt={prompt}" \
      -dictation-model /opt/models/whisper-large-v3-turbo-ct2
```

The script runs on the CPU with int8 weights and uses the machine's physical cores by default, at most 4 (`--threads` overrides it): more threads were slower in every measurement so far, on a laptop and on an 8-vCPU server, where 8 threads took 140 s for a take that 4 did in 84 s. It checks that the WAV is 16 kHz mono 16-bit and prints the transcript. Nothing is downloaded at dictation time: the model must already be on disk. The script has been checked with a stub library; its real transcription path still needs a run on a machine with faster-whisper and a model installed.

## Channels

The Channels icon in the side panel (or `/channels`) shows agent-created subjects, participants, and messages live (see Channels and subagents below). Agents create and use channels when instructed by you or when they need to coordinate; you don't write in channels, but you approve channels that reach outside an agent's family and can close any channel (Close channel). Direct user-to-agent messaging uses the separate agent `#ID` buttons.

### Channels and subagents

Agents talk to each other through channels, using the tools `agents_list`, `channel_create`, `channel_send`, `channel_list` and `channel_read`. An agent can end its own subagents (and theirs) with `subagent_terminate`, without asking; it cannot end any other agent, a sibling or itself. A message sent to a channel lands in every other member's transcript, marked as coming from that channel, and wakes them. Who may join whom:

- a top-level agent: any other top-level agent (in any project) and its own subagents;
- a subagent: its parent, its siblings, and its own subagents. Its parent can still add it to one of the parent's own channels.

Within an agent's family (its subagents, its parent, its siblings) a channel opens at once. A channel that includes anyone outside it, such as another top-level agent, always waits for your approval, whatever the agent's policy: the card names each outside member with its title, project, status and latest task, and the first message if the agent gave one (`channel_create` takes an optional `message`). Once open, messages on it flow without asking. Closing a channel tells its members and refuses further messages.

**Published channels.** A channel can also hold just one agent: ask an agent to open a channel with no one else, and it becomes an inbox for that agent once published. Publish (in the Channels tab) puts a channel on a link, `/xhaos/channel/<workspace>/<channel>`, and shows a random passphrase once, with a curl example; only its SHA-256 hash is kept. With `Authorization: Bearer <passphrase>`, a program outside Xhaos (a script, another Claude Code session) can `POST {"from": "name", "body": "…"}` (or a plain-text body with an `X-From` header) to send the channel's agents a message, which they receive marked as coming from outside and which wakes them, and `GET ?after=<message id>&wait=<seconds>` to read the channel, holding the request up to 60 s until a new message arrives. Reset passphrase issues a new one and stops the old; Unpublish stops it too; a closed channel cannot be published. Wrong passphrases are slowed down per address like sign-in attempts, and the link answers 503 while the server is locked. These messages are instructions from whoever holds the passphrase: agents still pass every tool call through their policy.

**Nodes.** Other machines (a build PC, a Raspberry Pi) can run commands for agents: install the separate `xhaos-node` program on them and they dial out to this server over one WebSocket at `/xhaos/node`, so they can sit behind NAT. The Nodes tab lists them as cards (online state, facts such as OS, CPU and memory, granted agents, running jobs). Add node issues a single-use join code (15 minutes; 1 hour for the Raspberry Pi first-boot files, which it can also generate) and shows the `install-node.sh` command once; for a Pi it gives the two first-boot files instead, and the `flash-node.sh` command that writes Raspberry Pi OS and them to an SD card from a Linux computer. A USB stick labelled `XHAOS` with an `xhaos-node.conf` gives a running node new Wi-Fi or a new join code, and the node writes its addresses back to the stick (off with `install-node.sh --no-usb-config`). A node works only inside its root folder, runs commands under Landlock unless installed with `--unsandboxed`, reaches devices only when listed with `--device`, and never uses sudo. Each card grants the node to chosen agents, which then get `nodes_list`, `node_run`, `node_job` and `node_copy`. The server needs `-node-url` (by default `https://` plus the first `-public-host`); see `docs/nodes.md` and `docs/deploy.md`.

`spawn_agent` starts a subagent in the parent's project, with the parent's policy and, unless it names another, the parent's model. It may name any model configured for the parent's provider (the same key); `models_list` lists them cheapest first with their prices, and the tool asks agents to pick the cheapest model that can do the task. The approval card shows the model. Its review mode is the same as the parent's write gate, so under manual review you approve each spawn. The subagent gets a channel with its parent, and its final answer is posted there automatically, waking the parent. A channel accepts at most 30 messages per 10 minutes, so two agents can't keep answering each other forever. Subagents nest at most three levels deep, and an agent can have at most eight unfinished subagents at once. An agent you paused still receives channel messages but stays paused until you resume it. Settings → Tools lists these tools, and the memory tools, next to the built-in ones. The Channels tab shows every channel and its messages live.

## Secrets

Settings → Secrets is the workspace's vault: named values such as a GitHub token, each with what it is for and the hosts it may reach. Values are encrypted with the key your passphrase unlocks (like provider keys) and never shown again, except with Reveal, which asks for the passphrase. Agents never see a value: `secrets_list` shows names, purposes, hosts and whether they may use each one.

A secret reaches an agent only after you grant it to that agent; none is granted by default. A `bash` call names the secrets it needs (`"secrets": ["GITHUB_TOKEN"]`) and refers to them as `$GITHUB_TOKEN`. Such a call always waits for your approval, whatever the agent's policy, and the approval card shows which secrets and hosts; trusting a secret to an agent (your passphrase again) lets its commands run as plain commands instead. The command runs in a sealed environment, on top of the sandbox:

- the secrets are environment variables of that one command;
- the project is read-only (except `.git`, so git can push), and its home, temp and cache folders are a throwaway folder deleted afterwards, so the value cannot be left in a file for a later command;
- it can connect only to the egress proxy, which the server runs on a local port and which lets it reach only the secrets' hosts (HTTPS on 443, or HTTP on 80), resolves names itself and refuses private, loopback and link-local addresses; UDP is blocked (no DNS lookups to carry a value out), and the proxy's lease ends with the command, closing its connections;
- the values, and their base64 and URL-encoded forms, are replaced with `[secret:NAME]` in its output before the model reads it.

**SSH keys** are a second kind of secret: paste the private key (ideally one made for this; if it has a passphrase, give it in Key passphrase: Xhaos stores the key unlocked, encrypted like every secret, and does not keep the key's passphrase) and list where it may connect as `[user@]host[:port]` (port 22 by default), e.g. `deploy@192.168.1.47` or `git@github.com`. A command given it can run plain `ssh`, `scp`, `sftp` or git over SSH to those hosts: its throwaway home gets the key file (`$NAME` is its path), an ssh config that uses it for its hosts and reaches them only through the proxy (the server's own binary is the `ProxyCommand`), and wrappers so `ssh` uses that config rather than the real home's `~/.ssh`, which the sandbox hides. Host keys are accepted on first connection and remembered with the secret. Any host, for either kind, may be an IP address; a private (LAN) address is reachable only when that exact host is listed, never through a `*.` pattern, and loopback never is.

Secrets need the sandbox and a kernel whose Landlock can restrict TCP (ABI 4, Linux 6.7+); otherwise commands with secrets are refused. Git over SSH does not go through the proxy: push with a token over HTTPS (for example `git push https://x-access-token:$GITHUB_TOKEN@github.com/owner/repo.git`). What a command does with a value inside its own run is not inspected: a command could still send it to one of the secret's own hosts, which is why each use asks unless you trusted it.

## Web

Agents read pages with `web_fetch(url)` (HTML becomes readable text: headings, lists, links, code and tables; long pages come in parts, like attachments) and search with `web_search(query)`. The search backend is chosen in Settings → Tools → Web: DuckDuckGo (no key; it reads DuckDuckGo's results page, best effort), Brave Search (an API key, encrypted at rest and never sent back), or your own SearXNG (its JSON format enabled; it may be on your LAN). The server makes these requests, never through a proxy, and checks every connection against the address it actually reaches (after DNS and on every redirect): localhost, private and link-local addresses (cloud metadata included) are refused, so a link or a DNS answer cannot turn a fetch toward your machine or network. Only `http`/`https`, no credentials in URLs, at most 5 MB per page. What comes back is labelled as untrusted for the model: a page may contain instructions, and they are not yours. Both tools are a "network" call: they ask under manual review and run under auto review, read-only agents included (nothing changes locally, but a URL can carry data out).

## Skills

Settings → Skills holds skills in Claude Code's format (a `SKILL.md` with a name and description, plus files): workspace skills uploaded as `.skill` files, and project skills found in each project's `.claude/skills/` or `.xhaos/skills/`, each with an on/off switch. Agents see the enabled ones by name and description, load one with `skill_read`, and run its scripts by naming it in a `bash` call (`$SKILL_<NAME>` is its folder, read-only). See [docs/skills.md](skills.md).

## Dangerously allow

From an agent's menu, **Dangerously allow…** lets that agent run, for the time you choose (15m, 1h, 4h, 1d, or your own like 10s or 1h30m; 10 seconds to 7 days), every call that would wait for you: writes, any command, commits and pushes, MCP tools. It takes your passphrase, is per agent (its subagents do not get it), shows a red badge with the time left on the card, is recorded in the agent's history, and ends on its own or with **Turn off dangerously allow**. Every agent normally stops after 40 model calls in a row until you write to it; under **Call limit** (folded away in the dialog) a session can raise that number, or switch the limit off. It lasts only for that session: when it ends, the agent is back to 40.

It does not lift the sandbox, the secrets rules (a command using a secret still asks unless you trusted that secret to the agent), the approval for channels to agents outside its family, or denials (a read-only agent stays read-only; blocked commits stay blocked). Turning it on switches nothing: the project's checkout stays on its branch, and the agent works on branches of its own (in worktrees under `.worktrees/`). Protected branches (`main`, `master`, `trunk`, `develop`, `production`, `release…`) and the checkout are guarded by git itself: around every command, if a protected branch moved, appeared or was deleted, it is put back (new commits stay in `git reflog`), and if the checkout changed branch it is switched back; the agent is told what was undone. Before a command runs, what could not be undone afterwards is refused: pushes to protected branches, force and `--all`/`--mirror`/`--tags`/`--delete` pushes, pushes that do not name their branch (`git push origin <branch>`), and deleting or renaming branches. That push check reads commands as text, so it stops mistakes rather than an agent determined to get around it (a script could push); what actually keeps pushes in check is that the agent has no credentials (the sandbox hides SSH keys and the SSH agent, and a token reaches it only as a secret you grant) and the remote's own branch protection.

## Cards, titles, usage and appearance

On a phone (600 px wide or less) the page shows one view at a time, with a navigation bar at the bottom: Agents (the message box and the agent cards, one column), then Questions (with its waiting badge), Files, Channels, Memories, Nodes and Settings, each full screen. Opening a panel by any means (a card's "answer the questions", a slash command, a link) switches to it, and opening an agent (a `#12` link) switches back; loading the page always starts on the agents. There is no Draw tab and no column choice on a phone, keyboard hints are hidden, and Allow/Deny are sized for fingers. Tablets keep the stacked layout (agents above, the panel below).

Where you are is kept in the URL hash, so a place can be bookmarked, reloaded, opened on another machine, or reached with the browser's Back button (no server routes involved): `#panel=settings&section=usage` (any side panel: `questions`, `files`, `channels`, `memories`, `settings`, `history`, `status`, `help`; Settings sections `models`, `usage`, `tools`, `appearance`, `security`), `#panel=channels&channel=5`, and `#agents=4,6,5`, the open cards: a link opens exactly those (and their parents) and closes the rest, scrolling to and highlighting the last; the link follows the cards you open and close. They combine with `&`. Settings → Appearance is also saved on the server, so every browser that signs in looks the same. The composer's unsent draft (text, attached agents and project) is kept in the browser as you type, so it survives a reload, a closed tab or a server restart; sending clears it. Agent replies render Markdown, tables included (static: cells wrap to the card's width). `#12` in a transcript or channel message links to agent 12's card. Switching panel adds a history step; opening cards and sections updates the current one.

An agent's card header shows its ID, project and title; the model it runs on is at the foot of the open card. When an agent starts from a prompt, its title is first the prompt's first line; at its first turn the agent's own model writes a 6–12 word title (a running agent's card shows a rotating phrase such as "Thinking…" inside the card, starting at a random phrase per agent; the header stays quiet) in one small, low-effort call, and the card updates live. A title you or a parent gave (`spawn_agent`'s `title`) is never replaced. The title is not part of the system prompt, so renaming never disturbs the prompt cache.

Every model call is counted per agent, model and purpose (turns, compaction summaries, titles, `/btw`): input (the whole prompt), the part read from or written to the provider's prompt cache, and output. Anthropic agents use automatic prompt caching: each turn reads the previous turns from the cache, billed at a small fraction of the input price. The total sits at the left of the side panel's tab bar (cost, or tokens while no model has a price); click it for Settings → Usage and cost, broken down by model (with each model's price) and by agent. Anthropic's published prices are built in; set or override any model's price there (USD per million tokens). Costs are computed when shown, so a price set later applies to past use.

Settings → Appearance (kept per browser): text size and transcript size (the interface scales as a whole), theme (dark, light, or the system's), accent colour (to try candidates for the brand colour), contrast, density, code font (JetBrains Mono by default, Fira Code, IBM Plex Mono, or the system's; used for transcripts, code and the message box), wrapping of long code lines, motion, timestamps (exact or relative), and whether typing `#12 ` in the message box attaches agent 12 (the default) or stays text (`\#12` always stays text). The fonts, Inter for the interface included, are bundled with Xhaos (from `@fontsource`), so they need no internet.

## Memory and compaction

Each agent's context is kept within its model's budget. A provider's context size (Settings → Models; empty uses 200,000 tokens for Anthropic and 128,000 for OpenAI-compatible) is the budget; when a request nears 80% of it, measured from the token counts providers report, the agent's own model summarizes the older part of the conversation. The cut falls only where nothing is split: before a user message, or after a finished round of tool calls. The model then sees the summary and the recent messages; the event log keeps the full history, and the transcript shows a "Context compacted" note with the summary. A provider error saying the request is too long also triggers a compaction and one retry. Later compactions fold in the previous summary.


The Memories icon in the side panel opens the current workspace's memories: short notes every agent in the workspace should know (a preference, a convention, a decision). Add, edit, and delete them there; Enter saves, Shift+Enter adds a line, and Escape cancels editing. With a backend they are stored on the server (notes an older version kept in the browser are moved there once, on connect) and stay live across tabs. Every agent's system prompt lists them, newest first, by their first line (up to 60); the prompt is rebuilt each turn, so the list survives compaction. Agents read one in full with `memory_read`, list them all with `memory_list`, and add or update one with `memory_save`, which is gated like a file write (under manual review you approve it); the panel marks memories an agent wrote. Without a backend, notes stay in this browser. Memories are separate from compaction: a summary belongs to its conversation, a memory to the workspace.

## Sketching

The composer's Draw tab is an [Excalidraw](https://excalidraw.com) board in dark mode. It loads on first use (its code is a separate chunk) and serves its fonts from this server, so nothing is fetched from a CDN. Boards belong to the workspace and live on the server. The picker above the canvas lists them; New board adds one, and Rename and Delete act on the open one. The drawing saves by itself a moment after you stop; a board that another page changes updates here without a reload. Images are stored once each, by content hash, and load when their board opens. A drawing an older version kept in this browser becomes a board named "Imported drawing" the first time Draw opens in a workspace with no boards; the browser's copy is then removed. Without a backend the tab has no boards to show. Attach the drawing to your next message as an image (PNG) or as Excalidraw data: the `.excalidraw` scene JSON, which a model can read and edit like code. Attachments are stored in this browser and not yet sent to backend agents.
